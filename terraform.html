Infrastructure as code, in Terraform

AWS and Azure described in code a team can change. New builds, and estates that are still a mixture of consoles, scripts, and memory.

New platforms and adopted ones

  • Modular Terraform, so the next service is not a copy of a thousand-line file
  • GitOps layering, so environment differences are deliberate
  • Multi-account AWS, including ECS, EKS, Lambda, and the network around them
  • Azure PaaS brought under code: App Services, WebJobs, Functions, and the related platform
  • A layout another engineer can review without a guided tour

The pipeline that sits on the code

  • Azure DevOps, AWS CodePipeline, and Bitbucket Pipelines
  • Promotions that are the same path every time
  • Quality gates that can actually fail a release
  • A rollback that has been thought about before it is needed
  • Manifest and artefact deployment, not only infrastructure

HashiCorp certified, and already in production

Neil holds the HashiCorp Certified Terraform Associate credential. The production record is a multi-account AWS organisation and a globally distributed Azure PaaS platform, both governed through modular Terraform and GitOps, plus full AWS environments delivered with Terraform, CodePipeline, and Bitbucket. At Fransystems that is the core of the practice: design, build, and manage both clouds as code.

Bringing an existing platform under Terraform is often the more useful engagement. The Azure work that matches this most closely is App Services and WebJobs that were moved under code, with Azure DevOps pipelines for what gets deployed on top. The point is an estate the team can change on purpose.

Code follows a decision. If the target shape is still open, start with architectural advice. If the code also needs to close an access path or a secret-handling gap, that is security work in the same change. If you are not sure the current design should be codified as it stands, a cost review can come first.
