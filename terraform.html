Your cloud setup, written down so it can be rebuilt

The network, the accounts, and the hosting, written down. They stay reliable as you grow, and a release follows the same path every time, on Amazon and Microsoft.

What the code buys you

Clicking the setup together works until the person who clicked it is away. Terraform keeps the shape you agreed: the network, the accounts, and the hosting are a reviewed change, not a memory.

  • Resilient

    If something fails, there is a known state to rebuild from. The spare capacity and the way back are in the design. They are not invented during the incident.

  • Scalable

    The next account, country, or service reuses what you already wrote. You grow by editing that, not by copying last quarter’s clicks.

  • Deployable

    One automatic path takes the change through a test copy and then the live service. A release can be repeated. Undoing it means going back to the previous version. That path is the pipeline work.

  • Secure

    Who can log in, what the network allows, and where passwords are kept are part of the review. A hole does not hide in a click nobody wrote down.

  • Recoverable

    The setup can be stood up again from the files. Recovery is something you have already tried, not a document from last year.

  • Efficient

    What exists is what the files say exists. Forgotten test systems and one-off exceptions show up, which is where the cost work starts.

How Fransystems builds it

New setups, and ones that are still a mixture of clicks and old scripts. The result is Terraform another person can change, with a release path that can refuse a bad change.

The setup

  • How the accounts are laid out, how the network is joined, and the boundaries around them
  • Amazon: several accounts, the services that run the applications, and the network they sit on
  • Microsoft: hosted web apps, background jobs, and the platform beside them
  • Shared building blocks, so a test copy differs from the live service on purpose
  • A layout another person can read without a guided tour

The release

  • Azure DevOps, AWS CodePipeline, and Bitbucket Pipelines
  • The same path every time, from the first test copy to the live service
  • Checks that can stop a release before customers see it
  • A way back, decided before anyone needs it
  • The application itself, as well as the computers and network underneath it
